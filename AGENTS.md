# AGENTS.md

Guidance for AI agents working on KaSH, a messaging aggregator in the manner of Ferdium, written in Kotlin with Compose for Desktop and Jewel.
`README.adoc` describes the project for humans, this file is about how to work on it.

## What it is

KaSH shows the web versions of messaging services (WhatsApp, and any web application as a custom service), each in a tab of a rail of icons with an unread badge, and a first tab, **Non lus** (Unread), that lists the conversations with unread messages of every service.
The design is the canvas https://claude.ai/artifact/PzwGyuaLy2yYJ7nkPfZk6q (artboards `Main`, `AddService`, `Settings`).

Each service is a Chromium profile of its own on disk (cookies, cache, IndexedDB, local storage, service workers), which nothing else shares and which is there again at the next launch.
**Persistence across restarts is the requirement that decides everything else**: never replace a service's profile by an in-memory one (an empty `cache_path`, an incognito context), even temporarily.
Chromium is JetBrains' fork of JCEF, built from the `jcef` submodule. It only runs on macOS for now.

**State of the services**: every service that KaSH knows is a **plugin** (see **Plugins** and `PLUGINS.adoc`): a manifest and a script, built in under `app/src/main/resources/app/kash/plugins/`. The built-in ones are WhatsApp, Google Chat, Slack and Google Messages. A web application that the user adds by its address is not a plugin: no option, no script, and it tells its total by its title (`(3) Name`). Adding a service to the catalog means inspecting its page once the user is logged in (see **Inspecting the services**) and writing its plugin. Plugins that the user installs are not loaded yet.
The automatic updates of the design (Settings › General › Updates) are not done.

## Modules

`app` → `browser` → `jcef-native` → `jcef/` (the JetBrains/jcef git submodule; not a Gradle module). `app` also uses `app-core` and `macos`.

| Module | Package | Role |
| --- | --- | --- |
| `app` | `app.kash` | The application: the main window (`MainWindow.kt`: title bar, `ServiceRail`, `InboxScreen` or a service's page; the selected service's header, `ServiceTitle` and `ServiceButtons` of `ServiceScreen.kt`, is in the title bar, so that its page has the whole height), `AddServiceWindow` (also Edit), `SettingsWindow`, `ConfirmDialog`, `ToastWindow`. `KashModel` holds the state and the loaded services, `Notifier` the notifications, `ServiceIcons` the favicons, the images that the user chose and those that the plugins give (and the plugins' squares). `BuiltInPlugins` loads the plugins of the resources, `PluginScripts` makes the script that a plugin's service is given (`plugin-api.js` and the plugin's). `ui/` has the theme (`KashTheme`, `KashColors`: the design's colors), the icons (`KashIcons`: the design's SVGs) and the strings (`Strings`: French and English). |
| `app-core` | `app.kash.core` | What is kept and decided, with no Compose and no JCEF, unit-tested: `Model.kt` (`Service`, `Settings`, `KashState`, `ProfileId`), `StateFile`, `WindowGeometry` (`WindowFile`), `KashDirectories`, `PluginManifest` (`PluginManifests.parse` and its checks), `PluginOptions` (normalizing, checking, the URL), `PluginIcon` (the image that a plugin gives), `PluginRegistry` (and `WebApplications`), `Inbox` (the rows, sorts, filter and badges of the Unread tab), `UnreadCount`, `NotificationPolicy`, `SquareColors`. |
| `browser` | `app.kash.browser` | Chromium behind a small API: `BrowserEngine` (starts and stops CEF, the message router, remote debugging), `BrowserProfile` (one request context on disk), `BrowserTab` (a page, its init scripts, the messages it sends, its `StateFlow`s, its AWT view). |
| `jcef-native` | (no code) | Builds JCEF from the submodule (`buildJcef`: CMake and Ninja), lays out the native bundle (`jcefBundle`), and exposes `jcef.jar` as its `api`. |
| `macos` | `app.kash.macos` | What macOS does that Java cannot: the Notification Center and the login item (SMAppService), in `native/kash_macos.m`, compiled into `libkash_macos.dylib` by `buildMacosLibrary` (clang of the Command Line Tools) and called through FFM. Only works in an application bundle (`inAppBundle`). |

**No `org.cef` type leaves `browser`**: `jcef-native` is only an `implementation` dependency of it. Keep it that way.

## Commands

```shell
git submodule update --init --recursive   # once: jcef, and its vcpkg submodule
brew install cmake ninja pkgconf bison     # once: what the build of JCEF needs
./gradlew build                            # everything, with the tests
./gradlew :app:run                         # opens the window
./gradlew :app:run -Pkash.inspect          # the same, with Chromium's remote debugging on 127.0.0.1:9222 (see Inspecting the services)
./gradlew :app:createDistributable         # KaSH.app, in app/build/compose/binaries/main/app
./gradlew :jcef-native:jcefBundle          # only JCEF
```

`-Dkash.support=<dir>` (a system property of the JVM that runs the app, for instance through `JAVA_TOOL_OPTIONS`) makes KaSH use another directory than `~/Library/Application Support/KaSH`: use it to test without touching the user's services.

## Inspecting the services

To write the plugin that reads a service's unread conversations (see `PLUGINS.adoc`), the service has to be inspected **once the user is logged in to it**, which only the user can do:

1. The user runs `./gradlew :app:run -Pkash.inspect` (port 9222, or `-Pkash.inspect=<port>`) and logs in to the service in KaSH.
2. The `kash-devtools` MCP server of `.mcp.json` (chrome-devtools-mcp, pinned, its usage statistics, CrUX lookups and update checks off) connects to `http://127.0.0.1:9222`. Claude Code loads it at its start: it has to be restarted after the app is running.
3. Read the **structure** of the page (the DOM, the elements that hold the unread counts and the conversations' names), never more of the user's messages than that takes.

The option is given only to the run task, as a system property (Compose replaces the run task's `jvmArgs`), and `Main.kt` refuses it in the application bundle: remote debugging lets any program of the machine read and drive the logged-in services.
`curl http://127.0.0.1:9222/json/list` lists the pages, one per service. A page can be read without the MCP server with the DevTools protocol over its `webSocketDebuggerUrl` (Node 22+ has `WebSocket` built in).

## JCEF

- **The jar and the native libraries come from the same commit**: the jar calls them through JNI. `jcef-native` builds both, and nothing takes `jcef.jar` from JetBrains' Maven repository.
- **To update JCEF**: move the submodule (`git -C jcef fetch --depth 1 origin <commit> && git -C jcef checkout <commit>`), on JetBrains' `dev` branch or a release tag of JBR that has `CefRequestContext.createContext(CefRequestContextSettings, …)`, then `./gradlew :jcef-native:jcefBundle` and check that the services still persist (see **Checking persistence**).
- The build uses Ninja, not JetBrains' `jb/tools/mac/build.sh`, which needs full Xcode and runs `brew link --force bison`. It downloads CEF and builds vcpkg's dependencies **inside the submodule**, which `.gitmodules` ignores (`ignore = untracked`). `jcef-native/python/sitecustomize.py` makes JCEF's tools accept the submodule's `.git` file as a checkout.
- **The CEF framework must be next to the helpers** (`Frameworks/Chromium Embedded Framework.framework`): a helper loads it from there, and Chromium aborts with "GPU process isn't usable" when it is missing. `BrowserEngine.start` gives CEF that path with `--framework-dir-path`, since JCefAppConfig expects JetBrains' layout (inside `cef_server.app`). The out-of-process server is not built into the bundle.
- **The JetBrains Runtime must not have JCEF** (`jbr_jcef`, `jbrsdk_jcef`): its `jcef` module would win over `jcef.jar`. `BrowserEngine.start` refuses to start on one. Foojay serves `jbrsdk_jcef` for the JetBrains vendor on macOS, so a machine without a plain JBR 25 installed gets the wrong one.
- JCEF needs `--add-exports` for `sun.awt`, `sun.lwawt`, `sun.lwawt.macosx` and `--enable-native-access=ALL-UNNAMED`: `app/build.gradle.kts` gives them to the run task and the packaged application.
- On ⌘Q, `Exception in thread "AppKit Thread" java.lang.NoSuchMethodError: handleBeforeTerminate` is printed: a bug of JetBrains' JCEF, whose native code (`native/client_app.cpp`, `util_mac.mm`) still calls `CefApp.handleBeforeTerminate()`, removed from its Java in 2023 (`7e14f0c1`). It is harmless (the exception is printed and cleared, and the quit goes on to KaSH's own shutdown): left as is, by the user's choice.
- **jpackage drops the executable bit** of the resources it copies into the bundle, and Chromium cannot start its helpers without it: `restoreExecutableBits` (after `createDistributable`) gives it back. `packageDmg` runs jpackage again and does not have that fix yet.

## Scripts in the pages

- A tab is created on `about:blank`; its init scripts are registered with `Page.addScriptToEvaluateOnNewDocument` through the browser's own DevTools session (`CefDevToolsClient`, which lives as long as the browser), then the service's address is loaded (`BrowserTab.created`). Loaded right away, the first document would not have them.
- **Blink only evaluates a session's scripts while its `Page` domain is enabled**: `Page.enable` is sent first. Without it the registration succeeds (`{"identifier":"1"}`) and the script never runs.
- The page is loaded **off** the DevTools callback (`whenCompleteAsync`): loading from it re-enters Chromium's observer list ("Check failed: … ObserverListReentrancyPolicy").
- **The pages see KaSH's theme as the system's**: `BrowserTab.setColorScheme` emulates `prefers-color-scheme` (`Emulation.setEmulatedMedia`) through the same DevTools session, before the first load and again whenever the theme changes (`KashModel.colorScheme`, set by `Main.kt`). A service whose own theme follows the system (WhatsApp's "System default") has KaSH's; one set to light or dark in its own settings keeps it. Popups that a page opens are pages of their own, without it.
- A page talks to KaSH with `window.cefQuery({request: "<JSON>"})` (CEF's message router, `BrowserEngine`), which arrives in `BrowserTab.messages`.
- `window.cefQuery` is **read-only** and not configurable (CEF defines it so): a test cannot wrap it to see what a script sends. Check what KaSH receives with a page that sends it (a scratch KaSH, a service of the right kind on a local page) and the `app.kash` DEBUG log.
- The scripts are in `app/src/main/resources/app/kash/`, and `Main.kt` says which service gets which (`scriptsFor`):
  - `notification-shim.js`, for every service: Chromium embedded here has **no** Web Notification API, and the script provides one that sends `{type: "notification", id, title, body, tag, silent}`. KaSH calls `__kashNotificationClick(id)` back when the notification is clicked, which fires its `click` event (a messaging service opens the conversation). A notification that a service worker shows itself (from a push) does not go through it.
  - for a plugin's service, its plugin's script with the API (`PluginScripts`, see **Plugins**).
- `KashModel.received` reads the messages: `unread` updates the service's conversations, `unreadCount` its total, `icon` its image (only from a plugin's service), `notification` goes to the `Notifier`. Its log has counts and an icon's host, never names, messages or addresses.

## Plugins

The format of a plugin, its manifest and the `kash` API are in `PLUGINS.adoc` (for the plugins' authors), `plugins/manifest.schema.json` and `plugins/kash-plugin.d.ts`. How KaSH implements them:

- **The built-in plugins** are the folders of `app/src/main/resources/app/kash/plugins/` that `index.json` lists, in the order of the catalog. `BuiltInPlugins.registry()` loads them at launch; one that is not valid is logged and left out, and `BuiltInPluginsTest` fails the build for it (every folder listed, every manifest valid, its script there, its URL resolved, and the JSON Schema's properties the same as `PluginManifest`'s). Changing the format means changing `PluginManifest`, `PluginManifests.check`, `manifest.schema.json` and `PLUGINS.adoc` together.
- **A service of a plugin** is saved with its plugin's id (`Service.plugin`) and its options (`Service.options`, normalized; a boolean is `"true"` or `"false"`). Its `name` and `url` are derived from its plugin (`PluginRegistry.refresh`): `KashModel` recomputes them at launch, when a service is added or edited, and when the language changes. A service whose plugin KaSH does not have keeps what was saved, without a script. Editing a service's options loads its page again: its script is given them.
- **A plugin's icon** (its manifest's `icon`, a file of its folder that `BuiltInPlugins` reads, `Plugin.icon`) is `ServiceIcon.Plugin` (after the image that the script gives, see below), which the Add service window offers first and selects for a new service of a plugin that has one (the site's icon otherwise); `ServiceIcons.pluginIcon` decodes it once, and `BuiltInPluginsTest` checks that Skia can. The tiles of the catalog show it too. WhatsApp, Google Chat, Slack and Google Messages have one (their logos): KaSH downloads a site's icon without cookies, and Google Chat's address, signed out, gives none.
- **The Add service window** is made from the manifests: a tile per plugin, then a field per option (`OptionField`: a text with its prefix, suffix and placeholder, a choice side by side or in a column, a check box), and the URL that they make (`PluginOptions.resolveUrl`) is the service's, which Add waits for.
- **The script of a plugin's service** (`PluginScripts.of`) is `plugin-api.js` as the body of a function of `config` (the plugin, the options as the script sees them, the language, `matches`) and `run`, the plugin's script as the body of a function of `kash`. The API runs it only in the top frame of a page that `matches` names (`*` is any run of characters), once per document (`__kashOpenConversation` is defined then), and catches what it throws. It checks what the plugin sends (an entry without an id, of an unknown kind or with a count under 1 is left out, with one warning in the console), sends a state only when it changed, and `watch` catches what `read` throws.
- **The image of a service** (`kash.setIcon`, `{type: "icon", source}`) replaces the plugin's icon or the site's when the service's icon is one of them (the user did not choose an image or a square): `tileContent` takes the image that its script gave, else the plugin's icon or the site's, else the plugin's square, else a globe. `PluginIcon.parse` takes an `https:` URL or the base64 `data:` URL of an image (1 MB at most, no SVG: Skia cannot decode it) and refuses the rest. `ServiceIcons.report` downloads it without the service's cookies (the page itself cannot read another site's image without CORS), keeps it in `<support>/service-icons/<service id>` (read at launch, before the script runs), keeps the image before when the new one cannot be had, and deletes it for `null`, and when the service is deleted or its data erased.
- `plugin-api.js` cannot be tested by the build (no JavaScript engine in it): after a change, check it in Node with a fake `window` and `cefQuery` (the API is a function body: `new Function('window', 'location', 'Node', 'console', 'setInterval', 'clearInterval', 'config', 'run', source)`), and `node --check` the scripts that `PluginScripts` makes.
- **WhatsApp** (`plugins/whatsapp/`, `matches` `https://web.whatsapp.com/*`): through `kash.watch`, every 2 s, it reads the unread conversations from WhatsApp Web's live model (`window.require('WAWebCollections').Chat`, as whatsapp-web.js does). `time` is the chat's last activity (`chat.t`, seconds, sent in milliseconds), which the Unread tab shows over the count (`TimeLabel`: the time today, "Hier" and the time yesterday, the date and the time on another day); the messages that the model holds in memory are not all of them, and are not that. The preview is what the row of the conversation shows in WhatsApp's list (`[data-testid="last-msg-status"]`: the text with the sender in a group, and the emojis, which are images, by their `alt`; its `title` attribute has neither), matched by the name in the row (`cell-frame-title`): the list is virtualized, so a conversation whose row was never rendered has none, and the row of the Unread tab shows what the conversation is instead. The model's last message is not that preview (a call, a group event, an internal placeholder, which WhatsApp words itself). Muted conversations (until a date, forever, auto-muted) and archived ones are left out, as WhatsApp leaves them out of its title's count; one marked as unread by hand (`unreadCount` -1) counts as 1. A group that was never named (no `formattedTitle`) is named by its members' first names without the user (found through `WAWebUserPrefsMeUser`), joined in the language of WhatsApp's interface (`Intl.ListFormat`: `Alice, Bruno et Chloé`), as WhatsApp shows it. Its `onOpenConversation` opens one (`WAWebCmd.Cmd.openChatBottom`). The model's names are internal to WhatsApp: when a version changes them, `read` throws, the API sends nothing and the page keeps working, and it has to be inspected again. IndexedDB (`model-storage`, store `chat`) holds the same data, but is written later than the model.
- **Google Chat** (`plugins/google-chat/`, `matches` `https://chat.google.com/*`, where its `url`, `mail.google.com/chat/u/0/`, redirects): Google Chat has no model that a script can reach (compiled code, nothing in IndexedDB), so every 2 s it reads the **side panel** (`[role="group"] [data-group-id]`: the sections starred, direct messages, spaces, apps; the Home list is not in a group). A row counts when it has Google Chat's badge (`.SaMfhe`, a compiled class name, the only thing that tells it): a direct message with its count, a **message request** (an account outside the organization: a row `data-group-id="pinned-item"`, one for all of them, whose id KaSH makes from the sender's name), a space only when the user is mentioned in it. A space with new messages and no mention is only in bold, without a badge, and is left out, as Google Chat leaves it out (the user's choice). The name of a person is the row's `[translate="no"]`, the name of a space the first line of its `[role="link"]` (a direct message's first line is the person's status, for screen readers). `time` is the row's `data-display-timestamp` (milliseconds). The preview is the Home list's (`[data-is-unread]` rows, `.Hkj4n`, without the rows of threads, `data-topic-id`), only while Home is shown, kept afterwards. The side panel loads its rows as it is scrolled: an unread conversation whose row is not loaded is not seen. Its `onOpenConversation` clicks its row, or loads `/app/chat/<id>` when the row is not loaded. **Not seen yet when it was written**: a mention in a space, and a muted conversation (whether Google Chat gives it a badge); check them when they happen.
- **Slack** (`plugins/slack/`, `url` `https://${workspace}.slack.com/`, `matches` `https://app.slack.com/*`, where the workspace sends after signing in; a Slack service is **one workspace**, the `workspace` option of its manifest, the design's *Espace de travail* field): Slack has no model that a script can reach, but its sidebar describes each conversation with attributes kept for its own tests, steadier than its classes (`[data-qa-channel-sidebar-channel-id]`, `…-channel-type`: `channel`, `im`, `mpim`; `…-channel-is-muted`; `…-is-you`), and its badge is `[data-qa="badge"]`. A conversation counts when it has a badge (the user's choices: like Slack): a direct message with its count, a channel only when the user is mentioned. A channel only in bold is left out, so are the muted ones and the user's own direct message. The name is `[data-qa^="channel_sidebar_name_"]`. The sidebar has no preview nor time. It is a virtual list: a conversation whose row is not rendered is not seen. Its `onOpenConversation` clicks its row, or loads `/client/<team>/<id>`. The replies in threads (the user's choice: only when Slack badges them) are one row, id `threads`, when Slack's Threads entry (`[data-qa="channel_sidebar_vall_threads"]`, at the top of the sidebar once there is a thread to see) has a badge, which it has when the user is mentioned in a thread; its name is Slack's own (`.p-channel_sidebar__name`, "Fils de discussion"), and opening it clicks the entry. The image of the workspace is the service's icon: Slack's button that switches accounts, `.p-account_switcher__team_icon--current`, has it as its `background-image` (`avatars.slack-edge.com`, public, `_88.png`, asked at `_132.png` for a Retina tile), or the class `c-team_icon--default` and the initials when the workspace has none (`setIcon(null)`).
- **Google Messages** (`plugins/google-messages/`, `url` `https://messages.google.com/web/`, `matches` `https://messages.google.com/web/*`; Messages for web, paired with the user's Android phone by a QR code): no model that a script can reach (Angular in production: an element's `__ngContext__` is a number, not its component; IndexedDB holds caches), so every 2 s it reads the **conversation list**, whose rows have attributes kept for its tests (`mws-conversation-list-item a[data-e2e-is-unread]`, `data-e2e-is-muted`, `data-e2e-is-pinned`; `[data-e2e-conversation-name]`, `[data-e2e-conversation-snippet]`). The id is the end of the row's `href` (`/web/u/0/conversations/<id>`). It shows no count: an unread conversation counts 1. Muted ones are left out. The list loads its rows as it is scrolled (50 first): an unread conversation whose row is not loaded is not seen. It shows no time, only a label (`mws-relative-timestamp`, in the page's language, English in KaSH): "Now", "3 min" today, which give the time to the minute, then a weekday (`.weekday-aria-label`, "Friday") or a date ("Nov 7"), which give the day (`timePrecision: 'day'`, the user's choice: the day, and the time today). Its `onOpenConversation` clicks the row, or loads the conversation's address. **Not seen yet when it was written**: a group (every conversation is `direct`), the label of a message of today after an hour ("1 hr" or "10:42 AM", both read), and of another year ("Nov 7, 2024" or "11/7/24", both read).

## Profiles

- **A profile is a direct child of the profiles root** (`KashDirectories.profile`, `BrowserEngine.profile` checks it). Chromium creates a profile only there: given `profiles/envs/<id>` it logs "Cannot create profile at path" and silently uses one that is not written to disk, **while `CefRequestContext.getCachePath()` still returns the path it was given**. Do not trust that method to check a profile.
- A profile id starts with `env-`, so that it is never one of the directories that Chromium keeps in the same root (`Default`, `Safe Browsing`…). A service's id and its profile's are distinct: **Erase all data** gives the service a new profile.
- A deleted service's profile, and an erased one, are deleted at the next launch, before Chromium starts (`KashState.deletedProfiles`): Chromium may still hold their files while it runs.

## Notifications

`Notifier` applies `NotificationPolicy` (notifications on, Do Not Disturb off, service enabled, not muted, its notifications on), then posts to macOS's Notification Center (`MacosNotifications`) when KaSH runs as KaSH.app, or shows `ToastWindow` (a window at the top right of the screen that never takes the focus) otherwise.
The Notification Center needs the bundle to be **launched by Launch Services** (`open`, the Finder, the Dock): launched by running its executable from a terminal, macOS answers "Notifications are not allowed for this application" without asking.
Its log never says what a notification says: that is the user's messages.

## The window

The main window opens where it was, as big and in the mode it was in when KaSH was closed, as KaTTY's does (the same code): `WindowFile` keeps it in `window.json`, apart from `state.json`, since it changes whenever the window moves. `keepWindowGeometry` (`WindowPersistence.kt`) writes it 500 ms after the last change and when KaSH quits. The position and the size kept are the floating window's, also while it is maximized or full screen (what it goes back to); a minimized window changes nothing, and a place that is on no screen any more (`sanitized`) becomes the platform's.

## Threads

- JCEF initializes and finishes its shutdown **on Swing's thread**. `BrowserEngine.start` (in `main`, before Compose starts) and `BrowserEngine.shutdown` (from `Dispatchers.IO` when quitting) wait for it, so they must never run on Swing's thread.
- Closing a profile waits for its cookies to be written: `KashModel` does it on `Dispatchers.IO`.
- Quitting (the close button, ⌘Q, the Dock) goes through `Kash`'s `quit`: it saves the state, closes each profile, stops Chromium, then exits. The system's Quit is intercepted for that: ending the process without it can lose the last writes of the profiles.
- **A build while KaSH runs used to make it impossible to quit** (⌘Q, the menu's Quit, IntelliJ's stop did nothing; only Force Quit did): the run task started KaSH on the jars of `build/libs`, which a build rewrites in place, and the classes that KaSH had not loaded yet, those of quitting (`MainKt$Kash$quit$1$1$5`), were read from the new jars: `NoClassDefFoundError` in the quit handler, after `quitting` was set, so every next Quit was ignored. The run task now starts KaSH on a copy of the project's jars made when it starts (`app/build/dev/classpath/<time>`, see **Running the app**). Each step of quitting also goes on when the one before throws.
  - `Hangs.kt` stays, for what else could keep KaSH from quitting: `watchEventThread` writes what the threads do (whole Java stacks, locks) to `<support>/hangs/<time>-event-thread-stuck.txt` when Swing's thread has not answered for 10 s (the system's Quit goes through it), and `haltIfNotQuitIn` stops the process 60 s after the quit started, with `<time>-quit-stuck.txt` (the state and the window are saved before). `BrowserEngine.shutdown` logs each step with how long it took.
  - While KaSH is stuck, `jcmd <pid> Thread.print` gives the Java stacks and `sample <pid> 3` the native ones (the main thread of AppKit, which Java does not show). A KaSH stopped from IntelliJ no longer prints to its console: its log is lost from then on.
- The handlers of `BrowserEngine` and the callbacks of `libkash_macos` run on threads of their own: they only set `StateFlow`s or post to Swing's thread.

## The page view

A service's page is Chromium's native view (`CefRendering.DEFAULT`) in a `SwingPanel`: native input, IME, scrolling, context menus and popups come with it. It is drawn **over** anything Compose draws in its area, so:

- **The menus are windows of their own** (`ui/WindowMenu.kt`: Jewel's `MenuContent` in an undecorated window under its button, which closes when it loses the focus or on Escape), never Jewel's `PopupMenu`, which is drawn in the window, under the page. Compose's `compose.layers.type=WINDOW` was meant to do that, but the window it made for a menu stayed 1×1 pixel at the top left of the screen (Compose 1.12.2, Jewel 0.42, JBR 25): the menus did not open. Its frame (`MenuFrame`: Jewel's menu background, a border, rounded corners, a shadow in a transparent margin of the window) is drawn by KaSH: Jewel's `MenuContent` draws only the items. A menu needs a width of its own (the design's), and a button that toggles it goes through `MenuState`, so that clicking it while the menu is open closes the menu instead of reopening it. A window that shows a `menuAnchor` provides `LocalAwtWindow`.
- **The editing shortcuts** (⌘C, ⌘V, ⌘X, ⌘A, ⌘Z, ⇧⌘Z) do nothing in a page by themselves: in Chrome they are the Edit menu's, which sends `copy:` to the focused view, and KaSH's menu bar has none. `EditShortcuts` (`browser`, a `CefKeyboardHandler` of the client) runs them on the focused frame (`CefFrame.copy()`…) once the page had its chance (`onKeyEvent`: a page that handles one keeps it). The key is read by its character in the keyboard's layout (`unmodified_character`).
- Tooltips are still Compose's popups: one that would go over a page is drawn under it.
- A test cannot check that a menu stays open by launching KaSH from a terminal: macOS (14 and later) gives the focus back to the terminal, which closes the menu. Only a real click tells.
- A confirmation is a dialog window (`ConfirmDialog`), never something drawn over the page.

Every enabled service is loaded at launch (`KashModel`), hidden, so that it notifies before it is first shown: its view is created by `CefBrowser.createImmediately()` and moved into the `SwingPanel` of whichever screen shows it.
**A page that is not shown is laid out at the size of the last page shown** (`BrowserTab.applyHiddenSize`, `Emulation.setDeviceMetricsOverride` through the browser's DevTools session; the window's size until a page is shown, `BrowserEngine.setHiddenPageSize`), and at its view's own once shown (`Emulation.clearDeviceMetricsOverride`). Without it, a page never shown is 0×0 (its native view is in no window), and a service that draws only the rows that fit (Slack's sidebar, a virtual list) draws none: its plugin read nothing until the user showed it. The size is given once the service's address has loaded, then whenever the view is shown or hidden: given at `onAfterCreated`, it crashed Chromium (SIGSEGV in `ExecuteDevToolsMethod`, no view yet).
**A view is shown only once Chromium created its browser** (`BrowserTab.created`, from `onAfterCreated`; `ServicePage` waits for it): a service that was just added is selected at once, and a view shown before its browser exists stayed gray until the user left the service and came back (JCEF drops the `setWindowVisibility` that it is given before, so the native view stays hidden).
**Links open in the system's browser** (`Links.kt`, the user's choice): a window that a service's page opens (`target=_blank`, `window.open`; `onBeforePopup`) to another site than the service's goes to the system's browser (`Desktop.browse`), and so does a click in the page to another site than the service's and the page's (`onBeforeBrowse`: a gesture, a `GET`, not a redirect). What stays in KaSH: the service's site (`siteOf`: the last two labels of the host, three under `co.uk` and the like, with no public suffix list), the sign-in pages of Google, Microsoft, Apple, Facebook and GitHub (a popup that signs in reports to its opener, in the service's profile), what the site does itself (redirects, forms that it posts), and what is not an address of the web (`about:blank`, `blob:`). `mailto:` and `tel:` go to the system when the user clicked. **An application's address is never loaded** (any scheme but the web's and Chromium's own, `PAGE_SCHEMES`: `slack://`, `zoommtg://`), in a page, a frame or a popup, even when the site sends there itself: Chromium cannot load it ("ERR_UNKNOWN_URL_SCHEME" in place of the page), and Slack sends to `slack://…/magic-login/…` after signing in; the page stays where it is (Slack's offers to use it in the browser). Only its scheme is logged: the rest can be a sign-in's token. Google's redirector (`google.*/url?q=`) is followed to where it leads. The addresses are not logged. The popups that stay are native windows of Chromium, in the same profile. DevTools open in a window of their own (the "…" menu).

## Checking persistence

The tests do not start Chromium. After a change to `browser`, `jcef-native` or the submodule, check by hand, with `-Dkash.support` on a scratch directory: a custom application on a fixed local origin writes a cookie, localStorage and IndexedDB, KaSH is quit with ⌘Q, started again, and the page reads them back in its service and not in another one.

## Jewel

- **`VerticallyScrollableContainer` takes its `ScrollState` by name** (`VerticallyScrollableContainer(modifier, scrollState = rememberScrollState())`): given first, positionally, it selects the overload of a `ScrollableState`, which does not scroll its content itself (the caller has to apply `verticalScroll`). The scrollbar is there, the content does not move: the Unread tab, Settings and the Add service window did not scroll.

## Running the app

`./gradlew :app:run` starts the JVM from `app/build/dev/KaSH.app` (`devBundle`), a bundle whose executable is a copy of the toolchain's `java` launcher, with links to the JDK's `lib`, `conf`, `legal` and `release` next to it: started as `java`, macOS takes the process for the JetBrains Runtime's (`com.jetbrains.jbr.java`), and ⌘Tab says "java" whatever `-Xdock:name` says. Its identifier, `app.kash.dev`, is not the application's (`app.kash`): `inAppBundle` is false in it, so the inspection port is allowed and the notifications take the fallback window. Gradle refuses an executable that is not its toolchain's, so the run task gets a `JavaLauncher` whose installation is the bundle's `Contents`, and its executable is set again in `doFirst` (Compose sets it after the script).
The run task also starts KaSH on **a copy of the project's own jars** (`app/build/dev/classpath/<time>`, made in its `doFirst`; the copies of earlier launches are deleted, which a KaSH that still runs does not notice: it keeps its jars open). A build while KaSH runs rewrites the jars of `build/libs` in place, and KaSH would read the classes it had not loaded yet from the new ones. The JCEF bundle (`prepareAppResources`) is not copied: it changes only when JCEF is built again.
**Never delete those links with `File.deleteRecursively()`**: it follows them, and emptied the JDK's own `lib`, `conf` and `legal` once (the JBR had to be restored from the same build). `devBundle` deletes the links as links first.

Starting the app opens a window on the user's desktop.
**One KaSH per support directory**: `Main.kt` locks `kash.lock` in it, and a second KaSH on the same directory shows "KaSH is already open" and exits. Without it, the second one could not use the profiles (Chromium locks them for the first one): its services were not the logged-in ones and showed nothing. Before launching KaSH, check that none runs on the same directory (`pgrep -f app.kash.MainKt`, and the instance's `kash.support`).
Never type into it with synthesized keystrokes, never take a full-screen screenshot, and stop only the instance you started (by process id). Quit it as the Dock does (`NSRunningApplication.terminate()`), not with a signal, which skips the clean shutdown.

## Build conventions

The Gradle build follows the Kodein conventions (the `kodein-gradle-kotlin-project` skill): Kotlin DSL, everything from `gradle/libs.versions.toml`, typed project accessors, `jvmToolchain` from `jvm.toolchain` in every module, repositories in `settings.gradle.kts` only, every catalog plugin declared in the root with `apply false`, and a comment for every line that is not obvious.
Every task that a build script registers has a `group` and a `description`.
