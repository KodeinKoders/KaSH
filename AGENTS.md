# AGENTS.md

Guidance for AI agents working on KaSH, a messaging aggregator in the manner of Ferdium, written in Kotlin with Compose for Desktop and Jewel.
`README.adoc` describes the project for humans, this file is about how to work on it.

## What it is

KaSH shows the web versions of messaging services (WhatsApp, and any web application as a custom service), each in a tab of a rail of icons with an unread badge, and a first tab, **Non lus** (Unread), that lists the conversations with unread messages of every service, in two sections: **Messages** (what the services count) and **Sujets** (Topics: what a service shows without counting it, a channel in bold without a mention; `Conversation.topic`, `Inbox.sections`, which no badge counts, not the rail's, not the Dock's).
The design is the canvas https://claude.ai/artifact/PzwGyuaLy2yYJ7nkPfZk6q (artboards `Main`, `AddService`, `Settings`).

Each service is a Chromium profile of its own on disk (cookies, cache, IndexedDB, local storage, service workers), which nothing else shares and which is there again at the next launch.
**Persistence across restarts is the requirement that decides everything else**: never replace a service's profile by an in-memory one (an empty `cache_path`, an incognito context), even temporarily.
The services and the settings are in `state.json` (`StateFile`), the installed plugins in `plugins.json` (`InstalledPluginsFile`): a value that a version does not know (an enum's, from another branch or a later version) is read as its default (`coerceInputValues`), and a file that still cannot be read is **set aside** (`<name>.unreadable-<time>`, next to it, `setAside`) before KaSH saves anything over it, never replaced: it once was, by an empty state, and every service was lost. Both are written forced to the disk, then moved in place (`writeDurably`).
Chromium is JetBrains' fork of JCEF, built from the `jcef` submodule. It only runs on macOS for now.

**State of the services**: every service that KaSH knows is a **plugin** (see **Plugins** and `PLUGINS.adoc`): a manifest and a script, built in under `app/src/main/resources/app/kash/plugins/`. The built-in ones are WhatsApp, Google Chat, Slack, Google Messages, Telegram, Discord, Instagram, Messenger, LinkedIn and Teams. A web application that the user adds by its address is not a plugin: no option, no script, and it tells its total by its title (`(3) Name`). Adding a service to the catalog means inspecting its page once the user is logged in (see **Inspecting the services**) and writing its plugin. The user installs other plugins in Settings › Plugins (see **Installed plugins**).
The automatic updates of the design (Settings › General › Updates) are not done.
**`SERVICES.adoc` says what KaSH does for each service** (YES, NO, TODO), and for those to come (TikTok, Snapchat): a change to a plugin, or something that it was not seen doing and now is, changes it too.

## Modules

`app` → `browser` → `jcef-native` → `jcef/` (the JetBrains/jcef git submodule; not a Gradle module). `app` also uses `app-core` and `macos`.

| Module | Package | Role |
| --- | --- | --- |
| `app` | `app.kash` | The application: the main window (`MainWindow.kt`: title bar, `ServiceRail`, `InboxScreen` or a service's page; the selected service's header, `ServiceTitle` and `ServiceButtons` of `ServiceScreen.kt`, is in the title bar, so that its page has the whole height), `AddServiceWindow` (also Edit), `SettingsWindow`, `ConfirmDialog`, `ToastWindow`. `KashModel` holds the state and the loaded services, `Notifier` the notifications, `ServiceIcons` the favicons, the images that the user chose and those that the plugins give (and the plugins' squares). `BuiltInPlugins` loads the plugins of the resources, `PluginInstaller` those that the user installs (`PluginsPage`: Settings › Plugins), `PluginScripts` makes the script that a plugin's service is given (`plugin-api.js` and the plugin's). `ui/` has the theme (`KashTheme`, `KashColors`: the design's colors), the icons (`KashIcons`: the design's SVGs) and the strings (`Strings`: French and English). |
| `app-core` | `app.kash.core` | What is kept and decided, with no Compose and no JCEF, unit-tested: `Model.kt` (`Service`, `Settings`, `KashState`, `ProfileId`), `StateFile`, `WindowGeometry` (`WindowFile`), `KashDirectories`, `PluginManifest` (`PluginManifests.parse` and its checks), `PluginPackage` (the files of a plugin that is installed), `InstalledPlugins` (`InstalledPluginsFile`, `PluginSource`, `PluginUpdates`), `ServiceOrder`, `PluginOptions` (normalizing, checking, the URL), `PluginIcon` (the image that a plugin gives), `PageLanguages` (the languages that the pages are given), `PluginRegistry` (and `WebApplications`), `Inbox` (the rows, sorts, filter and badges of the Unread tab), `UnreadCount`, `NotificationPolicy`, `NotificationReads` (when a notification's message was read), `SettingsDraft` (Settings' draft over the current settings), `SquareColors`, `Zoom` (the pages' zoom, and `UiScales`, KaSH's text). |
| `browser` | `app.kash.browser` | Chromium behind a small API: `BrowserEngine` (starts and stops CEF, the message router, remote debugging), `BrowserProfile` (one request context on disk), `BrowserTab` (a page, its init scripts, the messages it sends, its `StateFlow`s, its AWT view). |
| `jcef-native` | (no code) | Builds JCEF from the submodule (`buildJcef`: CMake and Ninja), lays out the native bundle (`jcefBundle`), and exposes `jcef.jar` as its `api`. |
| `macos` | `app.kash.macos` | What macOS does that Java cannot: the Notification Center and the login item (SMAppService), in `native/kash_macos.m`, compiled into `libkash_macos.dylib` by `buildMacosLibrary` (clang of the Command Line Tools) and called through FFM. Only works in an application bundle (`inAppBundle`). |

**No `org.cef` type leaves `browser`**: `jcef-native` is only an `implementation` dependency of it. Keep it that way.

## Commands

```shell
git submodule update --init --recursive   # once: jcef, and its vcpkg submodule
brew install cmake ninja pkgconf bison     # once: what the build of JCEF needs
./gradlew build                            # everything, with the tests
./gradlew :app:run                         # opens the window
./gradlew :app:run -Pkash.inspect          # the same, with Chromium's remote debugging on 127.0.0.1:9222 (see Inspecting the services)
./gradlew :app:createDistributable         # KaSH.app, in app/build/compose/binaries/main/app
scripts/install.sh                         # builds KaSH.app and installs it in ~/Applications (or --dest <folder>), not while it runs there
./gradlew :jcef-native:jcefBundle          # only JCEF
```

`-Dkash.support=<dir>` (a system property of the JVM that runs the app, for instance through `JAVA_TOOL_OPTIONS`) makes KaSH use another directory than `~/Library/Application Support/KaSH`: use it to test without touching the user's services.

## Inspecting the services

To write the plugin that reads a service's unread conversations (see `PLUGINS.adoc`), the service has to be inspected **once the user is logged in to it**, which only the user can do:

1. The user runs `./gradlew :app:run -Pkash.inspect` (port 9222, or `-Pkash.inspect=<port>`) and logs in to the service in KaSH.
2. The `kash-devtools` MCP server of `.mcp.json` (chrome-devtools-mcp, pinned, its usage statistics, CrUX lookups and update checks off) connects to `http://127.0.0.1:9222`. Claude Code loads it at its start: it has to be restarted after the app is running.
3. Read the **structure** of the page (the DOM, the elements that hold the unread counts and the conversations' names), never more of the user's messages than that takes.

The option is given only to the run task, as a system property (Compose replaces the run task's `jvmArgs`), and `Main.kt` refuses it in the application bundle: remote debugging lets any program of the machine read and drive the logged-in services.
`curl http://127.0.0.1:9222/json/list` lists the pages, one per service. A page can be read without the MCP server with the DevTools protocol over its `webSocketDebuggerUrl` (Node 22+ has `WebSocket` built in).

## JCEF

- **The jar and the native libraries come from the same commit**: the jar calls them through JNI. `jcef-native` builds both, and nothing takes `jcef.jar` from JetBrains' Maven repository.
- **To update JCEF**: take KaSH's patches out of the submodule (`git -C jcef checkout -- .`: `checkout` refuses to move it over modified files), move it (`git -C jcef fetch --depth 1 origin <commit> && git -C jcef checkout <commit>`), on JetBrains' `dev` branch or a release tag of JBR that has `CefRequestContext.createContext(CefRequestContextSettings, …)`, **check for each patch of `jcef-native/patches` whether the new commit fixed its bug** (read the code that it changes, and what it calls: a fix elsewhere leaves the patch applying, useless) and drop the patches that are not needed any more, then `./gradlew :jcef-native:jcefBundle` (which applies the others) and check that the services still persist (see **Checking persistence**). JetBrains rewrites `dev` (a force-push dropped `4d6c007`, the commit before `70e07e9`): a commit that is not on it any more may not be fetched, so move to the branch's head. Since `70e07e9`, `CefRequestContext.createContext` makes the context once CEF is initialized (at once when it is, as in KaSH), refuses to create a browser in a context that is not made, and logs "requested cache path … was not honored" and makes none when Chromium did not take the profile's path.
- The build uses Ninja, not JetBrains' `jb/tools/mac/build.sh`, which needs full Xcode and runs `brew link --force bison`. It downloads CEF and builds vcpkg's dependencies **inside the submodule**, which `.gitmodules` ignores (`ignore = untracked`). `jcef-native/python/sitecustomize.py` makes JCEF's tools accept the submodule's `.git` file as a checkout.
- **The CEF framework must be next to the helpers** (`Frameworks/Chromium Embedded Framework.framework`): a helper loads it from there, and Chromium aborts with "GPU process isn't usable" when it is missing. `BrowserEngine.start` gives CEF that path with `--framework-dir-path`, since JCefAppConfig expects JetBrains' layout (inside `cef_server.app`). The out-of-process server is not built into the bundle.
- **The JetBrains Runtime must not have JCEF** (`jbr_jcef`, `jbrsdk_jcef`): its `jcef` module would win over `jcef.jar`. `BrowserEngine.start` refuses to start on one. Foojay serves `jbrsdk_jcef` for the JetBrains vendor on macOS, so a machine without a plain JBR 25 installed gets the wrong one.
- JCEF needs `--add-exports` for `sun.awt`, `sun.lwawt`, `sun.lwawt.macosx` and `--enable-native-access=ALL-UNNAMED`: `app/build.gradle.kts` gives them to the run task and the packaged application.
- On ⌘Q, `Exception in thread "AppKit Thread" java.lang.NoSuchMethodError: handleBeforeTerminate` is printed: a bug of JetBrains' JCEF, whose native code (`native/client_app.cpp`, `util_mac.mm`) still calls `CefApp.handleBeforeTerminate()`, removed from its Java in 2023 (`7e14f0c1`). It is harmless (the exception is printed and cleared, and the quit goes on to KaSH's own shutdown): left as is, by the user's choice.
- **KaSH patches JetBrains' JCEF** (`jcef-native/patches/*.patch`, made with `git -C jcef diff`): `patchJcef`, which `buildJcef` depends on, applies each one to the submodule's checkout unless it is already applied (`git apply --reverse --check`), so the submodule shows them as modified files. One that does not apply after the submodule moved fails the build: make it again, or drop it when JetBrains fixed it. `on-pre-key-event.patch`: JCEF never called `CefKeyboardHandler.onPreKeyEvent` (`native/keyboard_handler.cpp` checked that the `BoolRef` it made was there with `!jboolRef`, which is its value, false for every key event), and every page got KaSH's shortcuts.
- **A build of JCEF while KaSH runs rewrites the `libjcef.dylib` that it loaded** (the same file, the copy of the resources): the run task copies the project's jars, not the JCEF bundle. Quit KaSH before building JCEF again.
- **jpackage drops the executable bit** of the resources it copies into the bundle, and Chromium cannot start its helpers without it: `restoreExecutableBits` (after `createDistributable`) gives it back. `packageDmg` runs jpackage again and does not have that fix yet.

## Scripts in the pages

- A tab is created on `about:blank`; its init scripts are registered with `Page.addScriptToEvaluateOnNewDocument` through the browser's own DevTools session (`CefDevToolsClient`, which lives as long as the browser), then the service's address is loaded (`BrowserTab.created`). Loaded right away, the first document would not have them.
- **Blink only evaluates a session's scripts while its `Page` domain is enabled**: `Page.enable` is sent first. Without it the registration succeeds (`{"identifier":"1"}`) and the script never runs.
- The page is loaded **off** the DevTools callback (`whenCompleteAsync`): loading from it re-enters Chromium's observer list ("Check failed: … ObserverListReentrancyPolicy").
- **The pages see KaSH's theme as the system's**: `BrowserTab.setColorScheme` emulates `prefers-color-scheme` (`Emulation.setEmulatedMedia`) through the same DevTools session, before the first load and again whenever the theme changes (`KashModel.colorScheme`, set by `Main.kt`). A service whose own theme follows the system (WhatsApp's "System default") has KaSH's; one set to light or dark in its own settings keeps it. Popups that a page opens are pages of their own, without it.
- **The pages are in KaSH's language** (Settings › General › Language), not macOS's: `KashModel` gives `BrowserEngine.setPageLanguages` the list of `PageLanguages.acceptLanguages` (`fr-FR,fr,en-US,en`, `en-US,en`), which `BrowserProfile.applyLanguages` sets as the profile's `intl.selected_languages` and `intl.accept_languages` preferences, Chromium's `Accept-Language` and `navigator.languages`. A site that follows the browser's language (Google Messages) is in it, one that follows its account's (Google Chat, Slack) keeps that one. Without it, every page was in English (CEF's `en-US,en`), whatever KaSH's language.
  - The preferences are set on Chromium's UI thread only (`setPreference` refuses another one), before each navigation (`onBeforeBrowse`) when they changed: a page has the new ones from its next load. Both are set: Chromium makes the accepted languages from the selected ones again (`LanguagePrefs`), and with only `intl.accept_languages`, the profile's old languages came back after the first request.
  - Not `CefRequestContextSettings.accept_language_list`: CEF prefers it to the preferences, which could then not change while KaSH runs.
  - Chromium's own locale (`CefSettings.locale`, `PageLanguages.locale`: its menus, its error pages, `Intl`'s default) is KaSH's language when it starts, and changes at the next launch.
- A page talks to KaSH with `window.cefQuery({request: "<JSON>"})` (CEF's message router, `BrowserEngine`), which arrives in `BrowserTab.messages`.
- `window.cefQuery` is **read-only** and not configurable (CEF defines it so): a test cannot wrap it to see what a script sends. Check what KaSH receives with a page that sends it (a scratch KaSH, a service of the right kind on a local page) and the `app.kash` DEBUG log.
- The scripts are in `app/src/main/resources/app/kash/`, and `Main.kt` says which service gets which (`scriptsFor`):
  - `notification-shim.js`, for every service: Chromium embedded here has **no** Web Notification API, and the script provides one that sends `{type: "notification", id, title, body, tag, silent}`, and `{type: "notification-close", id, after}` when the page closes it. Its ids are the document's (`n<random>-<n>`): KaSH keeps a group's last id across the page's reloads, and a counter that started again at `n1` in each document gave a click to another conversation's notification. KaSH calls `__kashNotificationClick(id)` back when the notification is clicked, which fires its `click` event (a messaging service opens the conversation); an id that the document does not have (it was loaded again since) sends `{type: "notification-click-missed", id}`, and `Notifier` opens the conversation that the plugin listed for it when it was clicked (`openConversation`). A notification that a service worker shows itself (from a push) does not go through it.
  - for a plugin's service, its plugin's script with the API (`PluginScripts`, see **Plugins**).
- `KashModel.received` reads the messages: `unread` updates the service's conversations (a `topic` one has a count of 0), `unreadCount` its total, `icon` its image and `contacts` its contacts and topics (both only from a plugin's service), `notification` goes to the `Notifier`. Its log has counts and an icon's host, never names, messages or addresses.
- **A conversation whose service gives no time** (Slack, Discord) takes the time when KaSH saw it (the user's choice, for every plugin that gives none): `UnreadTimes` (app-core, tested), applied by `KashModel.withSeenTimes` to each `unread` message. A conversation takes the time when it is first seen unread, and again when its count grows (a new message; a topic keeps its first one); one that is not unread any more is forgotten. One whose count is lower at a launch than when KaSH was closed (some read, or all of them then a new one, which the counts cannot tell) takes the time when KaSH saw it, as one that came while it was closed, after the time it had: its old time was wrong in the second case. It is kept across launches in `unread-times.json` (`UnreadTimesFile`, by service id, the conversations by a hash of their ids: WhatsApp's are phone numbers), written 5 s after a change, and at each `save` (at quit, with `until`, when KaSH last watched each loaded service).
  - For 60 s after its page was loaded (`SETTLE_MS`), a service's reports may be partial (a list still loading): what they do not show is kept, and what is new (or whose count grew) came while KaSH was not watching the service (KaSH closed, the service disabled), when that lasted over 60 s (`GAP_MS`) or KaSH never watched it: `WhileClosed(after = until)`. The Unread tab shows its time after a small clock (`KashIcons.Clock`), whose tooltip says that it is when KaSH received the message, not when it was sent, and that it came after `until` (or was already there). Settings › Unread › Show approximate times (`Settings.showApproximateTimes`, on by default) hides them: `Inbox.rows` gives those rows no time (last when sorted by date), while `UnreadTimes` still keeps them, for when it is on again.

## Plugins

The format of a plugin, its manifest and the `kash` API are in `PLUGINS.adoc` (for the plugins' authors), `plugins/manifest.schema.json` and `plugins/kash-plugin.d.ts`. How KaSH implements them:

- **The built-in plugins** are the folders of `app/src/main/resources/app/kash/plugins/` that `index.json` lists, in the order of the catalog. `BuiltInPlugins.registry()` loads them at launch; one that is not valid is logged and left out, and `BuiltInPluginsTest` fails the build for it (every folder listed, every manifest valid, its script there, its URL resolved, and the JSON Schema's properties the same as `PluginManifest`'s). Changing the format means changing `PluginManifest`, `PluginManifests.check`, `manifest.schema.json` and `PLUGINS.adoc` together.
- **A service of a plugin** is saved with its plugin's id (`Service.plugin`) and its options (`Service.options`, normalized; a boolean is `"true"` or `"false"`). Its `name` and `url` are derived from its plugin (`PluginRegistry.refresh`): `KashModel` recomputes them at launch, when a service is added or edited, and when the language changes. A service whose plugin KaSH does not have keeps what was saved, without a script. Editing a service's options loads its page again: its script is given them.
- **A plugin's icon** (its manifest's `icon`, a file of its folder that `BuiltInPlugins` reads, `Plugin.icon`) is `ServiceIcon.Plugin` (after the image that the script gives, see below), which the Add service window offers first and selects for a new service of a plugin that has one (the site's icon otherwise); `ServiceIcons.pluginIcon` decodes it once, and `BuiltInPluginsTest` checks that Skia can. The tiles of the catalog show it too. WhatsApp, Google Chat, Slack, Google Messages and Telegram have one (their logos): KaSH downloads a site's icon without cookies, and Google Chat's address, signed out, gives none.
- **The Add service window** (also Edit, where only the edited service's own tile is shown, which cannot be picked: a service keeps its plugin) is made from the manifests: a tile per plugin, then a field per option (`OptionField`: a text with its prefix, suffix and placeholder, a choice side by side or in a column, a check box), and the URL that they make (`PluginOptions.resolveUrl`) is the service's, which Add waits for. A web application shows only its name, address, label and badge: it is saved with the other settings at their defaults (in Unread, notifications on, no quiet hours), never with what a plugin picked before it had, hidden. Its draft is the service's that it edits: `Main.kt` makes the window again (`key(model.editing)`) when Edit is asked for another service, or Add, while it is open (the same window kept the first one's draft, and Save turned the second service into the first one's plugin), and deleting the service edited closes it.
- **The script of a plugin's service** (`PluginScripts.of`) is `plugin-api.js` as the body of a function of `config` (the plugin, the options as the script sees them, the language, `matches`) and `run`, the plugin's script as the body of a function of `kash`. The API runs it only in the top frame of a page that `matches` names (`*` is any run of characters), once per document (`__kashOpenConversation` is defined then), and catches what it throws. It checks what the plugin sends (an entry without an id, of an unknown kind or with a count under 1 is left out, with one warning in the console), sends a state only when it changed, and `watch` catches what `read` throws.
- **The image of a service** (`kash.setIcon`, `{type: "icon", source}`) replaces the plugin's icon or the site's when the service's icon is one of them (the user did not choose an image or a square): `tileContent` takes the image that its script gave, else the plugin's icon or the site's, else the plugin's square, else a globe. `PluginIcon.parse` takes an `https:` URL or the base64 `data:` URL of an image (1 MB at most, no SVG: Skia cannot decode it) and refuses the rest. `ServiceIcons.report` downloads it without the service's cookies (the page itself cannot read another site's image without CORS), keeps it in `<support>/service-icons/<service id>` (read at launch, before the script runs), keeps the image before when the new one cannot be had, and deletes it for `null`, and when the service is deleted or its data erased.
- **Installed plugins** (Settings › Plugins, `PluginsPage.kt`; `PLUGINS.adoc` › Installing a plugin): from a zip, a folder or an address (`PluginSource`). `PluginInstaller` (`app`, never on Swing's thread) reads the source whole (`read`), and `PluginPackage` (app-core, tested) checks its files: the manifest, the script and the icon there, names that stay in the folder (`..`, absolute paths refused: *zip slip*), 200 files and 10 MB at most, the manifest at the zip's root or in its only folder (a zipped folder; `__MACOSX` and `.DS_Store` dropped). An address is `https:` (or `http:` on the same machine), a zip (`PK\3\4`) or a `manifest.json` whose script and icon are downloaded next to it, without cookies. A built-in plugin's id is refused; an installed one's is a replacement, confirmed with both versions. The confirmation shows the pages where the script runs (`matches`).
  - The files go to `<support>/plugins/.staging-<id>/`, which takes the place of `<support>/plugins/<id>/` in one move; `plugins.json` (`InstalledPluginsFile`) lists the installed plugins, their sources, whether they are watched, and their versions.
  - **The registry changes while KaSH runs**: `KashModel.plugins` is a state, the built-in plugins then the installed ones (`PluginInstaller.plugins`, an invalid one logged and left out); `ServiceIcons` reads it through a function and forgets a plugin's decoded icon when it changes (`onPluginChanged`). After an installation, an update or an uninstallation, the plugin's services take their names and addresses from it again, and **their pages are loaded again**, with its new script (or none: an uninstalled plugin's services stay, without one).
  - **Versions**: `versionCode` (an integer that each version makes greater, as Android's; `version` is only shown) tells a newer one (`PluginUpdates.isNewer`). A watched source (`watch`, a folder or an address) is read again (`readManifest`: only its manifest, or its zip) every 10 s for a folder, every hour for an address (and at launch); a greater `versionCode` goes into `KashModel.pluginUpdates`, is notified once per version and per launch (`Notifier.pluginUpdate`, KaSH's own notification, key `plugin|<id>`, whose click opens Settings › Plugins: `KashModel.openSettings`), and dots the settings' button (`RailModel.settingsDot`). Settings › Plugins installs it from its source again (`updatePlugin`), and so do, for a service of that plugin, an arrow at the bottom left of its tile in the rail (`RailModel.updates`, the unread badge's mirror), the first item of its context menu, and an **Update** button at the left of its buttons in the title bar (`ServiceButtons`): `KashModel.startPluginUpdate`, in the model's scope (`updatingPlugins` while it runs), whose failure is a dialog of its own (`pluginUpdateFailure`, `PluginUpdateFailureDialog`). A source that cannot be read is logged once per error.
  - What Settings › Plugins does is done at once, not at Apply: these are no settings. A zip or a folder is chosen with AWT's `FileDialog` (macOS's own; a folder with `apple.awt.fileDialogForDirectories`).
- `plugin-api.js` cannot be tested by the build (no JavaScript engine in it): after a change, check it in Node with a fake `window` and `cefQuery` (the API is a function body: `new Function('window', 'location', 'Node', 'console', 'setInterval', 'clearInterval', 'config', 'run', source)`), and `node --check` the scripts that `PluginScripts` makes.
- **The contacts of the search** (`kash.contacts`): WhatsApp gives every conversation of its model (`set`: archived and muted ones too, the most recent first, not the status updates nor the broadcast lists, `@broadcast`); the others give the rows that their page shows (`add`): Google Chat its side panel's people and spaces (`dm/`, `space/`, not the message requests), Slack its sidebar's channels (`channel`), group and direct messages (not the user's own), Google Messages and Telegram their lists' rows, Discord its column's servers (`channel`), the direct messages that it shows (those with unread ones), and, while `/channels/@me` is shown, its list of every direct message (`[data-list-id^="private-channels"] a[href^="/channels/@me/"]`, whose `data-list-item-id` ends with the channel's id; a virtual list; the name is the row's `[class*="name_"]`, without the tag of a server that a user shows next to it, `[class*="chiplet"]`; a group has no `avatarStack_`, which a person's image has, with their status), which `onOpenConversation` clicks too.
- **WhatsApp** (`plugins/whatsapp/`, `matches` `https://web.whatsapp.com/*`): through `kash.watch`, every 2 s, it reads the unread conversations from WhatsApp Web's live model (`window.require('WAWebCollections').Chat`, as whatsapp-web.js does). `time` is the chat's last activity (`chat.t`, seconds, sent in milliseconds), which the Unread tab shows over the count (`TimeLabel`: the time today, "Hier" and the time yesterday, the date and the time on another day); the messages that the model holds in memory are not all of them, and are not that. The preview is what the row of the conversation shows in WhatsApp's list (`[data-testid="last-msg-status"]`: the text with the sender in a group, and the emojis, which are images, by their `alt`; its `title` attribute has neither), matched by the name in the row (`cell-frame-title`): the list is virtualized, so a conversation whose row was never rendered has none, and the row of the Unread tab shows what the conversation is instead. The model's last message is not that preview (a call, a group event, an internal placeholder, which WhatsApp words itself). Muted conversations (until a date, forever, auto-muted) and archived ones are left out, as WhatsApp leaves them out of its title's count; one marked as unread by hand (`unreadCount` -1) counts as 1. A group that was never named (no `formattedTitle`) is named by its members' first names without the user (found through `WAWebUserPrefsMeUser`), joined in the language of WhatsApp's interface (`Intl.ListFormat`: `Alice, Bruno et Chloé`), as WhatsApp shows it. Its `onOpenConversation` opens one (`WAWebCmd.Cmd.openChatBottom`). The model's names are internal to WhatsApp: when a version changes them, `read` throws, the API sends nothing and the page keeps working, and it has to be inspected again. IndexedDB (`model-storage`, store `chat`) holds the same data, but is written later than the model.

## The search

**The search** (`SearchWindow.kt`) lists the contacts and topics of every enabled plugin's service, read or unread, and opens one in its service (`KashModel.openConversation`, the plugin's `onOpenConversation`), as KaTTY's palette lists its commands.
- **What it lists**: each plugin reports its contacts and topics (`kash.contacts`, see `PLUGINS.adoc` › Reporting the contacts and topics) besides its unread conversations: `set` for every one of them (WhatsApp's model has all of them), `add` for what its page shows (a virtual list, the rows that it loaded, the list of another screen), which KaSH adds to those it saw before (`Directory.merge`, app-core, tested). `KashModel` keeps them in `contacts.json` (`DirectoryFile`, by service id, written 5 s after a change and at `save`), **with their ids and names as they are** (the user's choice: the search shows the names and opens the conversations by their ids; `unread-times.json` hashes them), and forgets a service's when it is deleted or its data erased, not when it is disabled. Its log has counts, never names.
- `Search` (app-core, tested) makes the lines (`Search.entries`: the contacts, then the unread conversations that are not among them, each once, with their counts; not Slack's `threads`) and matches them (`fuzzyMatch`, KaTTY's palette's: the letters in order, without regard for the case, **the accents** (each character folded alone, NFD, so that the indices are the text's; ł, ø, đ, ß, æ, œ, ı, which no decomposition takes an accent from, as their letter; a Korean syllable whole, which its decomposition would make its first letter; a query's combining marks left out) and the spaces; together, at the start of a word, in a short name is better). The Unread tab's filter folds its text the same way (`foldText`, `Inbox.filter`). Two sections, **Contacts** (`DIRECT`) then **Topics** (groups, channels), the user's choice; in each, the best match first, or the unread ones first with no query.
- **The field of the title bar** (`SearchField`, KaTTY's `PaletteButton`: a clickable row that looks like a text field) is the title bar's last child, in its middle: Jewel's title bar measures its children in their order and leaves out those that do not fit, and in a narrow window the field goes, not the service's buttons. The Unread tab's title is on the left, as a service's.
- **KaSH's shortcuts** (`BrowserShortcut`): ⇧⌘K the search, ⌘0 the Unread tab, ⌘1 to ⌘9 the enabled services of the rail in their order (`KashModel.shortcut`; none past the last), and Chrome's for the page of the service shown (none on the Unread tab; in a service's page only, not in DevTools nor a popup, whose browsers are the client's too: `PageShortcuts`' `isTab`, where ⌘[ moved the service back instead of changing DevTools' panel): ⌘+ and ⌘−, ⌘R (reload), ⌘[ and ⌘] (back, forward: the keys that type `[` and `]`, or the keys at their places on a QWERTY keyboard, `KEY_OPEN_BRACKET`, which are `^` and `$` on an AZERTY one, where `[` and `]` need ⌥; not tried on one), ⌥⌘I (the developer tools). The menus of a service show them at the right of their rows. In a page, `PageShortcuts.onPreKeyEvent` reads a digit by its key code (`windows_key_code`, the key's place, as Chrome reads its ⌘1: the key of 1 types `&` on an AZERTY keyboard), the window by its `Key` (`windowShortcutOf`, `ShortcutsTest`).
- **⌘⇧K** (the user's choice: not ⌘S, nor ⌘⇧F, which WhatsApp takes) opens and closes it: in a page, `PageShortcuts.onPreKeyEvent` takes it **before the page** (`browserShortcutOf`, tested; KaSH's, whatever the service does with it; the page gets neither its press nor its release) and gives it to `BrowserEngine.onShortcut` on Swing's thread. Before `on-pre-key-event.patch` (see **JCEF**), JCEF never called it: KaSH had the shortcuts of a page only through its window, and the page had them too (Google Chat opened its "Add people" on ⌘⇧K). AppKit gives a key with ⌘ to KaSH's window as well (AWT's view, which Chromium's is inside), so a key pressed in a page brings its shortcut twice, a few milliseconds apart: `ShortcutTwins` (`KashModel.shortcut(…, ShortcutSource)`, tested) does it once; elsewhere in the main window, its `onPreviewKeyEvent` (`isSearchShortcut`); in the search, its own. `KashModel.toggleSearch` does not open it again within 300 ms after it closed (a click on the field closes it first, when it loses the focus, as `MenuState`).
- **It is a window of its own** (`SearchWindow`), since a page is drawn over anything that Compose draws in the main window: undecorated, transparent, always on top, **exactly over the main window's content pane** (its bounds when it opens), whose veil (`#0E0F12` at 30 %, KaTTY's) and card (at most 640 dp, 90 dp from the top) are KaTTY's palette's (`SearchFrame`). It closes on a click on the veil, Escape, ⌘⇧K, when it loses the focus, and when a line is opened. ↑ and ↓ go round the list, which keeps the selected line in view (the first one too, which KaTTY's does not), Enter opens it; the selection is kept by its line while the list changes (`SearchWindowTest`, on `SearchContent`). **Not tried in the running application** when it was written: the window over the page, its focus, the shortcut in a page.

## Profiles

- **A profile is a direct child of the profiles root** (`KashDirectories.profile`, `BrowserEngine.profile` checks it). Chromium creates a profile only there: given `profiles/envs/<id>` it logs "Cannot create profile at path" and silently uses one that is not written to disk, **while `CefRequestContext.getCachePath()` still returns the path it was given**. Do not trust that method to check a profile.
- **The tabs' browsers are created one at a time** (`BrowserEngine.create`: the next one once `onAfterCreated` came for the one before, or its tab was closed). JCEF gives the browser that Chromium created to the Java object of the oldest one asked and not created yet (a queue, `LifeSpanHandler::OnAfterCreated` in `jcef/native/life_span_handler.cpp`), but each profile is read from disk first, and the browser of the one read first comes first: at a launch, every service's page was loaded in **another service's profile** (WhatsApp's in Google Messages', Google Chat's in WhatsApp's…), and all of them showed their sign-in pages; their own profiles were intact. A window that Chromium opens itself (a popup that stays in KaSH, DevTools) while a tab's browser is being created could still take its Java object.
- A profile id starts with `env-`, so that it is never one of the directories that Chromium keeps in the same root (`Default`, `Safe Browsing`…). A service's id and its profile's are distinct: **Erase all data** gives the service a new profile.
- A deleted service's profile, and an erased one, are deleted at the next launch, before Chromium starts (`KashState.deletedProfiles`): Chromium may still hold their files while it runs.

## Notifications

`Notifier` applies `NotificationPolicy` (notifications on, Do Not Disturb off, service enabled, not muted, its notifications on), then shows the notification as the settings say (Settings › Notifications › Notification style, `Settings.notificationStyle`): in `ToastWindow` (KaSH's own, a window at the top right of the screen that never takes the focus), or in macOS's Notification Center (`MacosNotifications`, the default), which only KaSH.app has: elsewhere (`./gradlew :app:run`) the notifications are KaSH's whatever the setting says, and Settings grays the system's out.
- KaSH becomes the Notification Center's delegate (`MacosNotifications.start`, which makes macOS ask the user for the authorization the first time) at launch when the settings use it, so that a click on a notification of the last launch still comes, and the first time a notification goes to it otherwise: a user of KaSH's own notifications is never asked.
- **KaSH's own notifications do not activate KaSH** when they are clicked, their cross neither: macOS brings an application to the front at a click on any of its windows, but a panel that does not activate it (`NSWindowStyleMaskNonactivatingPanel`), which AWT does not make. **AWT's `Window.Type.POPUP` does not** (measured on JBR 25: a `JFrame`, a `JWindow` or a `JDialog` of that type is an `AWTWindow_Normal` without the style, though its source sets it), and the first fix, which relied on it, did nothing. `ToastWindow` is a utility window (`Window.Type.UTILITY`, set in `SwingWindow`'s `init`, before it is shown: AWT refuses it afterwards), which AWT makes an `NSPanel` (`AWTWindow_Panel`), and once it is open `MacosWindows.makeNonactivating` (`kash_panel_make_nonactivating`, on AppKit's thread) finds it by its title (`KaSH notifications`) and gives it the style, `hidesOnDeactivate` off, and the window server's flag that the style sets at a panel's creation (`_setPreventsActivation:`, private, when the panel has it), which the style set later may not set (measured: the style, the flag and `hidesOnDeactivate` are set). A click on a notification itself shows its service through `KashModel.activateWindow`, which asks for the front (`Desktop.requestForeground`): `toFront` alone does not activate an application that is not in front. Its buttons (the cross, mark as read) show a background and a brighter icon under the pointer (`ToastButton`), so that a click on one is told from a click on the notification next to it; no tooltip, which the window, as big as the notifications, would cut. `ToastWindowTest` checks that the cross only closes, and draws the pointer over it (`build/renders/toast-hover-*.png`). **Not tried with a real click** when it was written.
- **A contact's notifications are one** (the user's choice): `NotificationGroups` (app-core, tested) groups them by their title in their service (the contact's name, a group's for a group: what WhatsApp's notifications say), and `Notifier` shows one per group, the last message, which the next one replaces (KaSH's own by its key, the Notification Center's by the same identifier). Its count is the notifications of the group since it was shown, or its conversation's unread messages when the plugin counts more (`NotificationGroups.conversationOf`: the unread conversation of the same name): a pill on KaSH's own (`Notifier.countOf`, live, as the plugin reports), the subtitle of the Notification Center's (`WhatsApp · 3 non lus`, as it was when it came); **only from 2** (the user's choice: a single message is the one shown). A click opens the page's last notification of the group. The group is over (its count starts again) when it is clicked, closed, or gone (a temporary one), and when what it says was read.
- **A notification goes once what it says was read** (the user's choice), in KaSH without it, on the phone, anywhere the service syncs: KaSH's own, and the Notification Center's (`MacosNotifications.remove`, `removeDeliveredNotificationsWithIdentifiers:`, whose identifier is the group's key). `NotificationReads` (app-core, tested) follows each group from its notification on, with what the plugins report (`Notifier.unreadChanged`): its conversation (by its title, `NotificationGroups.listedOf`, a topic too) was listed as unread and is not any more; or, for a notification whose title is no conversation's (or a web application's, which tells only its total), its service had something unread after it came and has nothing any more. Not the total at once: a notification often comes before the plugin's report of its message. A conversation listed **before** its notification came counts as listed (`shown`): otherwise reading it never ended the group, the bug that the user saw. Only the services whose page said what it has unread since it was loaded are judged (`KashModel.reporting`: a plugin's first report, a web application's first load ended): a page closed (a plugin's update, its options edited, the service disabled) or still loading seemed to have nothing unread, and ended its notifications; a deleted service's groups are over.
  - **The notifications of the last launch** that the Notification Center still shows (`MacosNotifications.delivered`, `getDeliveredNotificationsWithCompletionHandler:`, read 60 s after launch, `UnreadTimes.SETTLE_MS`): one whose conversation was listed then (`notification-reads.json`, `NotificationReadsFile`, the groups' keys hashed: they are contacts' names) and is not now goes, and so does one whose service has nothing unread or is gone; the others are followed as this launch's (`NotificationReads.restored`). A service that has not said what it has unread since the launch (`KashModel.reporting`: a page still loading, a service disabled, the network not up yet at a launch at login) is not taken for one that has nothing: its notifications wait for its first report, and every one of them went before. Their "Mark as read" button and their click find their conversation by the key's title (`NotificationReads.titleOf`, matched without case): the button did nothing, and the click gave the page the title as if it were a notification's id.
  - **A page that closes its notification** (`close()`, which `notification-shim.js` sends as `notification-close`, with how long after it was shown) ends its group when it is the group's last one, **for a web application only**: a plugin's service says what was read through its plugin, and a page may close its notifications after a while, read or not (Chrome takes them away then).
  - The `app.kash` DEBUG log says, for each notification, whether its title is a listed conversation's, and when a page closes one, after how long: which services' notifications follow their conversations, and which pages close them when they are read. Never a title.
- **Do Not Disturb's hours** (`QuietHours`, `DoNotDisturb`, app-core, tested; the user's choices): ranges (`QuietRange`: the days when it starts, ISO 1–7, from and to in minutes since midnight; one that ends before it starts ends the next day, one whose end is its start is the whole day), **global** (`Settings.quietHours`, Settings › Notifications › Do Not Disturb hours, in its draft) and **a service's own** (`Service.quietHours`, in its Edit window, under its notifications), edited by `QuietHoursEditor` (`ui/`: the days as toggles, the times written, `parseTime` takes "8:00", "21h30", "19h"; one that is not a time is framed as an error and not kept; `QuietHoursEditorTest` draws it to `build/renders/quiet-hours-*.png`).
  - Do Not Disturb is on (`DoNotDisturb.isOn`, `KashModel.doNotDisturb`) when the rail's switch is, or a global range is going on and was not lifted; a service is quiet (`DoNotDisturb.isQuiet`) when it is muted or in one of its ranges. `NotificationPolicy.decide(…, now)` reads both: a priority contact's notification goes through them all the same.
  - **The rail's bell** is crossed out during a global range, and says until when (`DoNotDisturb.until`, `QuietHours.endOf`, which follows the ranges that follow one another: "Monday to Friday 19:00–08:00" and the weekend's whole days are one quiet time; written as the Unread tab writes a time), and so does the title bar's chip. A click during a range **lifts it until it ends** (`Settings.quietResumedUntil`, an ISO local date and time), and the next one comes as planned; out of a range, the bell is the switch (`DoNotDisturb.toggle`).
  - `KashModel.now` is the time again at the start of each minute, so that the bell, the chip, the badges and the notifications follow the ranges by themselves.
  - **A service whose notifications are off** (muted, in one of its own ranges, or its notifications turned off in its Edit window; not KaSH's Do Not Disturb, which is all of them) has its unread badge in the rail dark gray, not red (`RailModel.quiet`, `UnreadBadge(quiet = …)`, `KashColors.quietBadge`, the user's choice; faded to 60 % first, which did not show enough). `RailBadgeTest` draws it (`build/renders/rail-badges-*.png`).
- **How long a notification stays** (Settings › Notifications › How long they stay, `Settings.notificationDuration`): KaSH's own are temporary (6 s, `TOAST_DURATION_MS`) or permanent (until they are clicked or closed; the window shows the last four, the others once those are gone; a new one of the same key replaces the one before). The Notification Center's are **macOS's to decide**: KaSH's alert style in System Settings › Notifications (banners, which go away; alerts, which stay), which no application can set. Settings shows it instead (`MacosNotifications.alertStyle`, `UNNotificationSettings.alertStyle`, read every 2 s while the page is shown) with a button that opens it (`open x-apple.systempreferences:com.apple.Notifications-Settings.extension?id=app.kash`, the panel without the `id` when that fails). `NSUserNotificationAlertStyle` in the `Info.plist` would only give the style before the user ever sets it: not used, banners are macOS's default.
- **Send a test notification** (Settings › Notifications) shows one as the draft of the settings would (its style and its sound, before Apply), whether or not the services may notify; it is KaSH's own (its icon, no service), and a click brings KaSH to the front. Settings says when macOS refuses KaSH's notifications (`MacosNotifications.authorization`, asked again after each test).
The Notification Center needs the bundle to be **launched by Launch Services** (`open`, the Finder, the Dock): launched by running its executable from a terminal, macOS answers "Notifications are not allowed for this application" without asking.
Its log never says what a notification says: that is the user's messages.

## The window

The main window opens where it was, as big and in the mode it was in when KaSH was closed, as KaTTY's does (the same code): `WindowFile` keeps it in `window.json`, apart from `state.json`, since it changes whenever the window moves. `keepWindowGeometry` (`WindowPersistence.kt`) writes it 500 ms after the last change and when KaSH quits. The position and the size kept are the floating window's, also while it is maximized or full screen (what it goes back to); a minimized window changes nothing, and a place that is on no screen any more (`sanitized`) becomes the platform's.

**Settings edits a draft** (until Apply or OK; Cancel drops it), which follows what changes elsewhere while Settings is open (the rail's Do Not Disturb, the title bar's theme, the Unread tab's sort): `SettingsDraft.rebase` (app-core, tested) gives each setting that the draft did not change its current value, setting by setting through `Settings`' JSON. The services' draft is only what was done in Settings › Services (their order once a row was moved, the switches toggled), which `KashModel.applyServices` applies to the services as they are then; OK applies only when something changed. Apply wrote back the whole draft of when Settings opened: it undid Do Not Disturb, a theme, a service moved or disabled in the rail meanwhile.

**The size of KaSH's text** (Settings › Appearance › Text size, `Settings.uiScale`, `UiScales.LEVELS` from 80 to 175 %, as KaTTY's): `ui/UiScale.kt` multiplies the `Density.fontScale` of each window's content by `LocalUiScale` (`UiScaled { … }`, which **every window** wraps its content in: the main one, Settings, Add service, the search, the menus, the notifications, the dialogs, About; a new window has to too). Only the text grows, the `dp` do not: an element that holds text takes a minimum height (`heightIn(min = …)`, `defaultMinSize`), never a fixed one, or its text is cut; what has to be fixed (the search field's width, a notification's height, which its window's size follows, a menu's width) is multiplied by `uiScaleFactor()`. `UiScaleRenderTest` draws a notification and the search at 100 and 175 % (`build/renders/ui-scale-*.png`).

**The zoom of the pages** (`Zoom`, app-core, tested): Chrome's levels (`Zoom.LEVELS`, 25 to 500 %), a service's own (`Service.zoom`, null for the default) or Settings › Appearance › Page zoom (`Settings.defaultZoom`), which only the services whose zoom was not changed follow. ⌘+ (⌘=, the keypad's +) and ⌘− zoom the service shown, in a page (`BrowserShortcut.ZoomIn`, `ZoomOut`, before the page) and elsewhere in the main window (`windowShortcutOf`); the "…" menu and the tile's context menu have Zoom in, Zoom out and back to the default (with its percent; enabled only when the service has its own). A menu's row shows its action's shortcut at its right, when it has one (`MenuRow(shortcut = …)`: `ZOOM_IN_SHORTCUT`, `ZOOM_OUT_SHORTCUT`). Not ⌘0, the Unread tab's. `KashModel.applyZooms` (at the end of each `update`) gives each loaded page its level when it changed (`BrowserTab.setZoomLevel`, Chromium's level, `ln(percent / 100) / ln(1.2)`), which the tab gives again at the end of each load: Chromium keeps a zoom by site in its profile, which a load of another site would not have.

## Threads

- JCEF initializes and finishes its shutdown **on Swing's thread**. `BrowserEngine.start` (in `main`, before Compose starts) and `BrowserEngine.shutdown` (from `Dispatchers.IO` when quitting) wait for it, so they must never run on Swing's thread.
- Closing a profile waits for its cookies to be written: `KashModel` does it on `Dispatchers.IO`.
- Quitting (the close button, ⌘Q, the Dock) goes through `Kash`'s `quit`: it saves the state, closes each profile, stops Chromium, then exits. The system's Quit is intercepted for that: ending the process without it can lose the last writes of the profiles. Its `QuitResponse` is kept and answered at the end, `performQuit()` once Chromium stopped: cancelled at once, as it was, it was a refusal, and macOS stopped the logout, the restart or the shutdown that asked.
- **A build while KaSH runs used to make it impossible to quit** (⌘Q, the menu's Quit, IntelliJ's stop did nothing; only Force Quit did): the run task started KaSH on the jars of `build/libs`, which a build rewrites in place, and the classes that KaSH had not loaded yet, those of quitting (`MainKt$Kash$quit$1$1$5`), were read from the new jars: `NoClassDefFoundError` in the quit handler, after `quitting` was set, so every next Quit was ignored. The run task now starts KaSH on a copy of the project's jars made when it starts (`app/build/dev/classpath/<time>`, see **Running the app**). Each step of quitting also goes on when the one before throws.
  - `Hangs.kt` stays, for what else could keep KaSH from quitting: `watchEventThread` writes what the threads do (whole Java stacks, locks) to `<support>/hangs/<time>-event-thread-stuck.txt` when Swing's thread has not answered for 10 s (the system's Quit goes through it), and `haltIfNotQuitIn` stops the process 60 s after the quit started, with `<time>-quit-stuck.txt` (the state and the window are saved before). `BrowserEngine.shutdown` logs each step with how long it took.
  - While KaSH is stuck, `jcmd <pid> Thread.print` gives the Java stacks and `sample <pid> 3` the native ones (the main thread of AppKit, which Java does not show). A KaSH stopped from IntelliJ no longer prints to its console: its log is lost from then on.
- The handlers of `BrowserEngine` and the callbacks of `libkash_macos` run on threads of their own: they only set `StateFlow`s or post to Swing's thread.

**The About window is a Compose window** (`AboutWindow.kt`, a `DecoratedWindow` of its own), as KaTTY's, not macOS's panel, which for a Java process says Java: it shows the logo, `APP_NAME`, `versionText()` (`Version 1.0.249 (3d58b41)`), `branchText()` (`Branch feature/x`, not for `main` nor a detached HEAD), `commitDateText()` (`Committed: 2026-11-03 19:43`, in the user's time zone), in KaSH's language, and "Made with love by Kodein Koders" with a `LinkAnnotation.Url` to https://kodein-koders.com. Escape and ⌘W close it. It opens from the About item of the macOS application menu (`takeAboutItem`, `Desktop.setAboutHandler`) and from the small entry at the bottom of Settings' column, an icon and its name (`KashModel.aboutOpen`). The Settings item of the same menu, after it (⌘, there), opens Settings as the rail's gear does (`takeSettingsItem`, `Desktop.setPreferencesHandler`).
`BuildConfig` (the gmazzo plugin, `app/build.gradle.kts`) has `VERSION`, the root `version`, written only there (the bundle's `packageVersion` is the same value: macOS wants a first number of 1 or more, and numbers only): `1.0` and, as its patch, **the number of commits that the current one comes after** (`git rev-list --count HEAD` less one, read when the build is configured, so a new commit makes the configuration cache miss; 0 outside a checkout, and a shallow clone counts only what it fetched, so a build to distribute needs the whole history), **plus one while the working tree has changes that are not committed** (`git status --porcelain --ignore-submodules=dirty` not empty: modified, staged or new files that are not ignored, and the `jcef` submodule moved to another commit, not what its build writes in it), so that a build before a commit and the build of that commit have the same version (the `GIT_COMMIT` of the first is still the commit before; only "clean" or "dirty" is the command's output, so the configuration cache misses when the tree becomes one or the other, not at each edit), `GIT_BRANCH` (`git branch --show-current`), `GIT_COMMIT` (`git rev-parse --short HEAD`, `unknown` outside a checkout) and `GIT_COMMIT_DATE` (`git log -1 --format=%cI`: the same for every build of the commit, so that `BuildConfig` is not compiled again at each build). `AboutWindowTest` checks them against git.
Adding a plugin to the root build script changes the classpath of every build script, which Gradle takes for a new implementation of `buildJcef`: it runs once again (Ninja rebuilds nothing that did not change).

## The page view

A service's page is Chromium's native view (`CefRendering.DEFAULT`) in a `SwingPanel`: native input, IME, scrolling, context menus and popups come with it. It is drawn **over** anything Compose draws in its area, so:

- **The menus are windows of their own** (`ui/WindowMenu.kt`: Jewel's `MenuContent` in an undecorated window under its button, which closes when it loses the focus or on Escape), never Jewel's `PopupMenu`, which is drawn in the window, under the page. Compose's `compose.layers.type=WINDOW` was meant to do that, but the window it made for a menu stayed 1×1 pixel at the top left of the screen (Compose 1.12.2, Jewel 0.42, JBR 25): the menus did not open. Its frame (`MenuFrame`: Jewel's menu background, a border, rounded corners, a shadow in a transparent margin of the window) is drawn by KaSH: Jewel's `MenuContent` draws only the items. A menu needs a width of its own (the design's), and a button that toggles it goes through `MenuState`, so that clicking it while the menu is open closes the menu instead of reopening it. A window that shows a `menuAnchor` provides `LocalAwtWindow`.
- **The editing shortcuts** (⌘C, ⌘V, ⌘X, ⌘A, ⌘Z, ⇧⌘Z) do nothing in a page by themselves: in Chrome they are the Edit menu's, which sends `copy:` to the focused view, and KaSH's menu bar has none. `PageShortcuts` (`browser`, the client's only `CefKeyboardHandler`: a `CefClient` ignores every one after the first) runs them on the focused frame (`CefFrame.copy()`…) once the page had its chance (`onKeyEvent`: a page that handles one keeps it). The key is read by its character in the keyboard's layout (`unmodified_character`).
- Tooltips are still Compose's popups (Jewel's `Tooltip`): one that would go over a page is drawn under it. **The rail's tiles** have one in a window of its own (`ui/WindowTooltip.kt`, `WindowTooltip`: undecorated, transparent, never focused, placed out of the rail once its content is measured, invisible until then): the service's name and its shortcut (`serviceShortcut`, ⌘1 to ⌘9; the Unread tab's ⌘0), after 600 ms over the tile, while KaSH's window is the active one, until the pointer leaves it, presses it (a click, a drag) or opens its menu. **Not tried in the running application** when it was written.
- A test cannot check that a menu stays open by launching KaSH from a terminal: macOS (14 and later) gives the focus back to the terminal, which closes the menu. Only a real click tells.
- A confirmation is a dialog window (`ConfirmDialog`), never something drawn over the page.
- **A service's tile in the rail has a context menu** (a right click, or a click with Control: `onContextClick` in `ServiceRail.kt`, which consumes the press so that the tile is not selected), a `WindowMenu` where the pointer is (`pointerAnchor`): `serviceContextMenu` (`ServiceScreen.kt`), updating its plugin when it has a new version, what the header's buttons do (back, forward, reload, mute), the "…" menu's actions, then disable and delete. Back and forward are enabled as the page could when the menu opened.
- **The services are reordered by dragging** a tile of the rail, or a row of Settings › Services (anywhere on it; its grip is a hint), with the same gesture: `Modifier.reorderable` (`ui/Reorder.kt`, `ReorderState`), which drags the element along its list, over the others, and makes it take its neighbor's place past half of it. The order is `ServiceOrder.moveNextTo` (app-core, tested): right after or right before the neighbor in the whole order, since the rail does not show the disabled services (`KashModel.moveNextTo` for the rail, Settings' draft until Apply).
  - **Each element is in a `key` of its id**: otherwise, once it takes another's place, it is another element of the composition, whose gesture is not the one going on, and the drag stops at its first move. The gesture reads the order and the callback as they are now (`rememberUpdatedState`): captured when it started, they were stale after the first move. Settings' drag did neither, and only its grip took it: it did not work at all.

Every enabled service is loaded at launch (`KashModel`), hidden, so that it notifies before it is first shown: its view is created by `CefBrowser.createImmediately()` and moved into the `SwingPanel` of the selected service's page when its service is selected.
**One panel for every service's page** (`ServicePage`, `PageHolder`), which the main window always has (without a size while the Unread tab is shown): going from a service to another changes the page in it, which is given its size before it is added (the page before's, the panel's last one). A new panel for each service, as it was, had no size yet when its page was added: the page was resized to nothing and back, and Chromium laid it out again and waited for a new frame of it, while it showed nothing for half a second.
**A page that was never shown is laid out at the size of the last page shown** (`BrowserTab.applyHiddenSize`, `Emulation.setDeviceMetricsOverride` through the browser's DevTools session; the window's size until a page is shown, `BrowserEngine.setHiddenPageSize`), and at its view's own from the first time it is shown (`Emulation.clearDeviceMetricsOverride`, **once**: removing the emulated size makes Chromium lay the page out again and wait for a new frame, even at the same size, and the page was empty for half a second each time it was shown). A page that was shown keeps its native view's size while it is hidden. Without it, a page never shown is 0×0 (its native view was never in a window), and a service that draws only the rows that fit (Slack's sidebar, a virtual list) draws none: its plugin read nothing until the user showed it. The size is given once the service's address has loaded, then when the view is first shown: given at `onAfterCreated`, it crashed Chromium (SIGSEGV in `ExecuteDevToolsMethod`, no view yet).
**A page still blinks the first time it is shown**: JCEF's native code sets the frame of its view before the frame of the view's container, which macOS then resizes the view with (autoresizing), and the page is laid out at twice its size, then at its size. Only a change to JCEF's native code (`updateView:` in `util_mac.mm`) would avoid it.
**A view is shown only once Chromium created its browser** (`BrowserTab.created`, from `onAfterCreated`; `ServicePage` waits for it): a service that was just added is selected at once, and a view shown before its browser exists stayed gray until the user left the service and came back (JCEF drops the `setWindowVisibility` that it is given before, so the native view stays hidden).
**Links open in the system's browser** (`Links.kt`, the user's choice): a window that a service's page opens (`target=_blank`, `window.open`; `onBeforePopup`) to another site than the service's goes to the system's browser (`Desktop.browse`), and so does a click in the page to another site than the service's and the page's (`onBeforeBrowse`: a gesture, a `GET`, not a redirect). What stays in KaSH: the service's site (`siteOf`: the last two labels of the host, three under `co.uk` and the like, with no public suffix list), the sign-in pages of Google, Microsoft, Apple, Facebook and GitHub (a popup that signs in reports to its opener, in the service's profile), what the site does itself (redirects, forms that it posts), and what is not an address of the web (`about:blank`, `blob:`). A plugin adds the addresses of a sign-in that KaSH does not know (`openInKash` in its manifest, `*` for any run of characters: Instagram's with Facebook, `https://www.facebook.com/oidc/*`), which its service's tab is given (`BrowserProfile.openTab`, `addressPattern`) and which stay in KaSH, clicked or in a window. `mailto:` and `tel:` go to the system when the user clicked. **An application's address is never loaded** (any scheme but the web's and Chromium's own, `PAGE_SCHEMES`: `slack://`, `zoommtg://`), in a page, a frame or a popup, even when the site sends there itself: Chromium cannot load it ("ERR_UNKNOWN_URL_SCHEME" in place of the page), and Slack sends to `slack://…/magic-login/…` after signing in; the page stays where it is (Slack's offers to use it in the browser). Only its scheme is logged: the rest can be a sign-in's token. Google's redirector (`google.*/url?q=`) is followed to where it leads. An address is read by `parseAddress`: Chromium keeps characters that `java.net.URI` refuses (`|`, `{`, `^`, a `%` that is not an escape), which are escaped and read again, and a host with `_`, which `URI` reads without a host, is its authority's (`hostName`); an address of the web that still cannot be read goes to the system when clicked or opened in a window. Unread, such a link to another site stayed in KaSH, in the service's profile. The addresses are not logged. The popups that stay are native windows of Chromium, in the same profile. DevTools open in a window of their own (the "…" menu).

## Jewel

- **Jewel's standalone theme does not ship the icons of IntelliJ that its components draw** (`AllIconsKeys`, looked up as resources of the classpath), and draws a pink square in place of one it cannot find: the combo boxes of Settings had one instead of their chevron. KaSH has the ones that its components use in its resources, at the path that Jewel looks for (`app/src/main/resources/expui/general/chevronDown.svg`, and `_dark` for the dark theme, which Jewel takes there; Jewel does not tint it). `JewelIconsTest` checks the path and that a combo box has no pink in either theme (`build/renders/combo-box-*.png`). A Jewel component that is used for the first time may need another one: Jewel's styles use `General.ChevronDown`, `General.ChevronRight` (a submenu), `General.CloseSmall`, `Actions.Close`, `Actions.Search`, `Actions.SearchWithHistory` and `Ide.External` (a link).

- **`VerticallyScrollableContainer` takes its `ScrollState` by name** (`VerticallyScrollableContainer(modifier, scrollState = rememberScrollState())`): given first, positionally, it selects the overload of a `ScrollableState`, which does not scroll its content itself (the caller has to apply `verticalScroll`). The scrollbar is there, the content does not move: the Unread tab, Settings and the Add service window did not scroll.

## Checking persistence

The tests do not start Chromium. After a change to `browser`, `jcef-native` or the submodule, check by hand, with `-Dkash.support` on a scratch directory: a custom application on a fixed local origin writes a cookie, localStorage and IndexedDB, KaSH is quit with ⌘Q, started again, and the page reads them back in its service and not in another one.

## Running the app

`./gradlew :app:run` starts the JVM from `app/build/dev/KaSH.app` (`devBundle`), a bundle whose executable is a copy of the toolchain's `java` launcher, with links to the JDK's `lib`, `conf`, `legal` and `release` next to it: started as `java`, macOS takes the process for the JetBrains Runtime's (`com.jetbrains.jbr.java`), and ⌘Tab says "java" whatever `-Xdock:name` says. Its identifier, `app.kash.dev`, is not the application's (`app.kash`): `inAppBundle` is false in it, so the inspection port is allowed and the notifications take the fallback window. Gradle refuses an executable that is not its toolchain's, so the run task gets a `JavaLauncher` whose installation is the bundle's `Contents`, and its executable is set again in `doFirst` (Compose sets it after the script).
**The Dock's badge (the unread total) does not show in a KaSH that the run task started**, only in one that Launch Services opened (KaSH.app from the Finder or the Dock, or `open`): KaSH gives it (`Taskbar.setIconBadge`, the `app.kash` DEBUG log says "Dock badge: 3", and `NSApp.dockTile.badgeLabel` has it), but macOS does not show it for a process that Gradle's daemon started, whatever its bundle's identifier, and does for the same command opened with `open`. Most likely the daemon is the process's responsible process, and the badge is its own, which has no icon. Not a bug of KaSH: check the badge in KaSH.app (`createDistributable`).
The run task also starts KaSH on **a copy of the project's own jars** (`app/build/dev/classpath/<time>`, made in its `doFirst`; the copies of earlier launches are deleted, which a KaSH that still runs does not notice: it keeps its jars open). A build while KaSH runs rewrites the jars of `build/libs` in place, and KaSH would read the classes it had not loaded yet from the new ones. The JCEF bundle (`prepareAppResources`) is not copied: it changes only when JCEF is built again.
**Never delete those links with `File.deleteRecursively()`**: it follows them, and emptied the JDK's own `lib`, `conf` and `legal` once (the JBR had to be restored from the same build). `devBundle` deletes the links as links first.

Starting the app opens a window on the user's desktop.
**One KaSH per support directory**: `Main.kt` locks `kash.lock` in it, and a second KaSH on the same directory shows "KaSH is already open" and exits. Without it, the second one could not use the profiles (Chromium locks them for the first one): its services were not the logged-in ones and showed nothing. Before launching KaSH, check that none runs on the same directory (`pgrep -f app.kash.MainKt`, and the instance's `kash.support`).
Never type into it with synthesized keystrokes, never take a full-screen screenshot, and stop only the instance you started (by process id). Quit it as the Dock does (`NSRunningApplication.terminate()`), not with a signal, which skips the clean shutdown.

## Build conventions

The Gradle build follows the Kodein conventions (the `kodein-gradle-kotlin-project` skill): Kotlin DSL, everything from `gradle/libs.versions.toml`, typed project accessors, `jvmToolchain` from `jvm.toolchain` in every module, repositories in `settings.gradle.kts` only, every catalog plugin declared in the root with `apply false`, and a comment for every line that is not obvious.
Every task that a build script registers has a `group` and a `description`.
